# v1.0 Public open-source launch: plan

_Written 2026-09-30, during the overnight run. The user approved v0.4 to v1.0 in advance. Going
public itself (the public repository, the PyPI release, the live Hub) is the owner's decision;
this plan builds everything up to it. Status is tracked in `tasks/todo.md` and
`docs/overnight-log.md`._

## Objective

Anyone can find, trust, try and contribute to OpenHealth:
- it has had a security review, and its checks run on every change;
- a clinician can write a pack from a guide, without Python;
- a pack PR is validated, tested, evaluated and given a card automatically;
- the community has a code of conduct and a governance model;
- a release is one tag away.

**Exit (from the roadmap):**
- a new user goes from README to their own local validation in under 10 minutes;
- the sandbox runs with `docker compose up`;
- the Hub is live with five packs (the owner's go-ahead).

## Approach (one PR each)

### 1. Security review
- **A threat model** (`docs/security/threat-model.md`): assets, trust boundaries, and threats
  per STRIDE category, each with its mitigation and the test that checks it.
- **Security headers** on every response: CSP, frame-ancestors, nosniff, Referrer-Policy and
  Permissions-Policy (the dashboard needs no third-party origins).
- **Dependency audit** in CI: `pip-audit` on the locked Python dependencies, and `npm audit` on
  the Hub site's lockfile (high and critical fail).
- **API penetration test** in CI: an OWASP ZAP API scan (pinned image) of the running engine
  from its OpenAPI description, with sign-in on. Medium and higher alerts fail, unless an
  accepted-risk entry explains them.
- **`SECURITY.md`:** how to report a vulnerability, and what is in scope.

### 2. A clinician's pack-authoring guide and `openhealth new`
- **`openhealth new DIR --id namespace/name`:** a minimal pack that validates and passes its
  tests. It has one question with human-readable criteria, rules, a policy, three tests, a tiny
  dataset and a card, all in YAML.
- **The guide** (`docs/guides/authoring-a-pack.md`), written for a clinician:
  - writing questions and criteria in words;
  - rules;
  - the policy and risk levels;
  - behaviour tests;
  - a local dataset;
  - evaluation and the card;
  - publishing.

  Each step is one command, with the YAML shown.

### 3. The docs site
- **MkDocs Material** (pinned, a `docs` dependency group). It builds every page in `docs/`: the
  guides, the spec, the ADRs, the security documents and deployment.
- `mkdocs build --strict` in CI, so a broken link fails. Publishing the site waits for the repo
  to go public.

### 4. The contribution flow
- **A pack-PR workflow:** on PRs touching `packs/**`, each changed pack is validated, tested,
  evaluated on its benchmark dataset, compared with `main`'s benchmark and given a card. The
  job summary shows the metrics. A regression in a critical metric beyond the pack's tolerance
  fails (the roadmap's eval gate).
- **Community files:**
  - `CONTRIBUTING.md`: code and packs, the checks, the style;
  - `CODE_OF_CONDUCT.md`: Contributor Covenant 2.1;
  - `GOVERNANCE.md`: maintainers, decisions, how a publisher becomes verified or
    institutional;
  - issue and PR templates.

### 5. Release readiness and the 10-minute exit
- **A release workflow:** on a `v*` tag, build the sdist and wheel, run the tests against the
  wheel, and publish to PyPI by trusted publishing. It stays inert until the owner configures
  PyPI and pushes a tag.
- **CI job `quickstart`:** runs the README's quickstart as written, in a clean environment
  (install, run a pack, evaluate on a local dataset), and fails if it takes more than 10
  minutes.

## Decisions made on the owner's behalf
- **ZAP for the API penetration test.** It is the maintained open-source standard, runs from
  a pinned image, and reads the OpenAPI description the server already publishes.
- **MkDocs Material for the docs site.** Markdown in, no build step for authors, and the
  docs are already Markdown.
- **Contributor Covenant 2.1**, the most widely adopted code of conduct.

## Blocked on the owner
- The public repository, the PyPI release, the live Hub and site, and the docs site's hosting.
  Each needs the go-ahead, and accounts or secrets only the owner can create.

## Verification
- [ ] The ZAP scan, `pip-audit`, `npm audit` and the headers test are green.
- [ ] `openhealth new` → `validate` → `test` → `eval` works in CI (the guide's commands).
- [ ] `mkdocs build --strict` is green.
- [ ] A pack PR shows metrics against `main`, and a seeded regression fails.
- [ ] `quickstart` finishes under 10 minutes.
