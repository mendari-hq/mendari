# v0.6 Readiness for health organizations: plan

_Written 2026-09-30, during the overnight run. The user approved v0.4 to v1.0 in advance. Status
is tracked in `tasks/todo.md` and `docs/overnight-log.md`._

## Objective

A health organization can run OpenHealth itself, safely:
- people sign in with the organization's identity provider and act within their role;
- machines use API keys;
- every deployment of a pack is recorded, with its governance approval;
- performance is monitored over time, with alerts;
- PHI is handled by policy.

**Exit (from the roadmap):** a pilot organization could run the inbox router with its own IdP,
PHI-safe settings, monitoring and governance approvals.

## Constraints

- **Nothing changes until it is configured.** With no identity provider set, the server behaves
  exactly as today: open API, Vercel Authentication in front of production. Every new control
  switches on through settings, and production's settings are not changed tonight.
- **The rules still hold.** Policy only lowers automation, and risk level 4 is never automated
  (ADR-0002). A governance approval is the only way to lift a level 2–3 cap, and it is recorded
  on every decision it affects.
- **Additive schema changes only** (new tables and nullable columns), on SQLite and Postgres.

## Approach (one PR each)

### 1. OIDC login, roles and API keys
- **Login:** OpenID Connect authorization code with PKCE against the organization's IdP
  (`OPENHEALTH_OIDC_ISSUER`, `OPENHEALTH_OIDC_CLIENT_ID`, optional secret). The flow reuses the
  SMART machinery: `GuardedHttp`, id_token verification with the IdP's JWKS, and server-side
  sessions.
- **Roles:** `viewer`, `reviewer`, `service`, `governance` and `admin`, taken from a
  configurable claim (default `roles`, or groups mapped by `OPENHEALTH_OIDC_ROLE_MAP`).
  - viewer reads;
  - reviewer also decides, resolves reviews, records outcomes and gives feedback;
  - service (for API keys) reads, decides and records outcomes;
  - governance reads and approves automation;
  - admin does everything, including evaluations, exports and API keys.
- **API keys** for machine clients (EHR integrations, CDS Hooks, the sandbox worker). They are
  created by admins, shown once, stored as SHA-256, carry a role, and can be revoked. They're
  sent as `Authorization: Bearer ohk_…`.
- **Enforcement:** one middleware checks a permission table on every route when auth is on;
  a route that isn't listed needs `admin` (deny by default). Evaluations run only for
  admins (dashboard decision 4). The dashboard shows who is signed in and hides actions the
  role can't take.
- **Tenancy:** each user and key belongs to an organization, and decisions, reviews, feedback
  and reports are stored with it. Queries are filtered by it. One deployment can serve several
  organizations without their data mixing, and single-organization deployments are unchanged.

### 2. Deployments and governance approvals
- **A deployment registry:** which pack version (digest) runs where (an environment name), with
  which providers, since when, and who deployed it. It is recorded when the server starts and
  shown in the dashboard.
- **Governance approvals in the UI:** for a level 2–3 pack, a governance user can approve
  automation (approver, reference such as committee minutes, scope and expiry). It is stored,
  audited in the hash chain, and applied as the runtime's `GovernanceOverride`, which is already
  written into every affected decision. Level 4 has no approve button, and the API refuses it.

### 3. Monitoring
- **Over time, per pack and per site:**
  - observed accuracy (from reviews, outcomes and thumbs-downs);
  - the human-override trend;
  - confidence drift (the distribution of the primary confidence against the benchmark's);
  - automation rate;
  - cost per decision from provider pricing.
- **Alerts:** thresholds per pack (for example "observed accuracy below the benchmark minus the
  pack's degradation tolerance over the last 7 days") are checked on a schedule, shown in the
  dashboard, and optionally posted to a webhook. The webhook must be on the allow-list.
- A **Monitoring view** in the dashboard.

### 4. PHI mode
- `OPENHEALTH_PHI_MODE`:
  - `hash`: inputs are never stored, only their hash, whatever the pack's `audit.store_input`;
  - `encrypt`: inputs are stored encrypted with a key from `OPENHEALTH_PHI_KEY` (AES-GCM,
    `cryptography`), and decrypted only for roles that may see them;
  - `off`.
- **Retention:** `OPENHEALTH_RETENTION_DAYS` purges stored inputs (not the hash chain or the
  decisions) after N days, on a schedule.
- **Access logging:** every read of a stored input is recorded in the hash chain (who, when,
  which decision).
- A **PHI deployment guide** (`docs/deploying-with-phi.md`).

### 5. Container images and on-prem templates
- **A container image per pack:** the engine with only that pack. Built in CI on every change;
  pushed to GHCR (`ghcr.io/<owner>/openhealth-<pack>`) only for release tags, so nothing is
  published until someone tags a release.
- **On-prem templates:** a Helm-free Kubernetes manifest and a docker compose file for a site
  (engine, Postgres, the site's IdP settings, PHI mode on), with a checklist.

### 6. Pilot check
- A CI job runs the pilot scenario against a local OIDC provider in the compose network (a small
  test IdP):
  - an admin signs in and creates an API key;
  - the worker decides through the key;
  - a reviewer resolves;
  - governance approves a level 2 pack;
  - monitoring shows the week;
  - PHI mode `encrypt` is on, and a viewer can't read an input.

## Decisions made on the owner's behalf
- **A `service` role for machines.** A key for an EHR integration should decide and record
  outcomes, but not resolve reviews, which is a clinical act.
- **Tenancy lives in a context variable** (`core/tenancy.py`), set by the auth middleware. The
  store filters every read and stamps every write with it, so no route can forget it.
- **Approvals are bound to the pack's digest.** A new version of a pack needs a new approval,
  because what was approved is the pack as reviewed.
- **The deployment registry is recorded at startup, only when something changed** (pack digest,
  providers or environment), because serverless platforms start the server many times a day.
- **PHI encryption uses AES-256-GCM from `cryptography`,** which the project already depends on
  (through `PyJWT[crypto]`), with the decision id as associated data. A ciphertext can't be moved
  to another decision.

## Verification
- [ ] With no settings, every existing test passes unchanged (the open mode).
- [ ] Each role can do exactly its actions: a matrix test over every route.
- [ ] API keys are stored hashed, revocable and scoped. Sessions expire.
- [ ] Tenancy: one organization never sees another's decisions (a test per list endpoint).
- [ ] A governance approval lifts a level 2–3 cap only within its scope and expiry, level 4 is
      refused, and approvals are chained.
- [ ] PHI `hash` stores no input. `encrypt` stores only ciphertext and decrypts by role.
      Retention purges. Reads are logged.
- [ ] Monitoring numbers match a hand computation on seeded history. An alert fires once.
- [ ] The pilot job passes.

## Risks
- **Locking people out.** Open mode stays the default, and settings are validated at startup.
- **Cross-tenant leaks.** Every query is filtered by organization, with a matrix test per
  endpoint.
- **Key management for PHI encryption.** The key comes from the environment (or a KMS in a
  site's own setup); the guide says how to rotate it.
