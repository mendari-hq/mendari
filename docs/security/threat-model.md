# Threat model

_Mendari engine, dashboard and registry, as of v1.0 (2026-09-30). Reviewed before the
public launch; update it with any change to a trust boundary. The checks named here run in CI._

## What we protect

| Asset | Why it matters |
|---|---|
| Decision inputs (messages, records; PHI in a real deployment) | Patient privacy. |
| Decisions, reviews, outcomes and the audit hash chain | Clinical accountability: what was decided, by what, and who changed it. |
| Governance approvals | They lift the automation cap at risk levels 2–3. |
| Sessions, API keys, OIDC and SMART tokens | Whoever holds them acts as a clinician, an integration or an admin. |
| Provider credentials (Jev, LLM gateway keys) | Cost, and a channel to send data out. |
| Pack integrity (signed archives, publisher keys) | A tampered pack changes clinical logic at every site that pulls it. |
| PHI encryption key | It opens every stored input. |

## Trust boundaries

1. **Browser ↔ engine:** the dashboard and the API.
2. **EHR ↔ engine:** CDS Hooks, SMART launch, DTR and FHIR decide.
3. **Engine → outside servers:** FHIR servers, the CQL engine, the identity provider, the payer
   and alert webhooks.
4. **Engine → model providers:** Jev, and LLMs through a gateway.
5. **Registry ↔ clients:** pushing and pulling packs.
6. **Engine ↔ database:** SQLite or Postgres.

## Threats and mitigations (STRIDE)

| # | Threat | Boundary | Mitigation | Checked by |
|---|---|---|---|---|
| S1 | Someone uses the API or dashboard without an account | 1, 2 | With sign-in configured, every route has a permission and unlisted routes need admin (deny by default). The Vercel deployment sits behind Vercel Authentication. | `test_every_route_has_the_permission_it_should`; ZAP scan with sign-in on |
| S2 | A forged `id_token`, replayed sign-in or open redirect | 1 | PKCE S256, state and nonce used once, `id_token` verified with the issuer's JWKS, `next` limited to this site. | `tests/test_auth.py`; `pilot-check` against a real OIDC provider |
| S3 | A stolen API key | 2 | Keys are stored as SHA-256, shown once, bound to one organization and a machine's role (`viewer` or `service`; review and approval are a person's), and revocable. They expire: 90 days unless asked, 365 at most; keys from before Phase 4 expire 30 days after the first start of that release. Expired and revoked keys are refused in the lookup itself, as is a key with no expiry. Optional scopes narrow a key to the routes they name (a scoped key reaches nothing else). Managing keys and clients is a people-only permission (`keys`), so no key, an old admin key included, can mint a credential that outlives it, and creating and revoking a key are chained (`key:<id>`, without the key). Keys are accepted in the `Authorization` header only, never in a URL or a form, and `/api` answers are `no-store`. | `test_api_keys_work_for_machines_are_hashed_and_revocable`, `test_keys_are_managed_by_people_only`, `test_new_keys_are_for_machines_only`, `test_an_expired_key_is_refused_like_any_credential_that_is_not_valid`, `tests/test_api_keys.py` (SQLite and Postgres), `test_a_credential_in_a_url_or_a_form_is_refused`, `test_api_answers_are_never_stored` |
| S5 | Credential confusion: a junk, foreign or revoked bearer credential falls back to a session cookie | 1, 2 | An `Authorization` header decides alone, the scheme is matched in any case, and the credential's prefix picks the one store it is checked against (`ohk_` keys; `mat_` access tokens, refused unless SMART Backend Services is on); anything else is a `401` with `error="invalid_token"`, one generic answer that never echoes the credential. | `test_a_credential_that_is_not_valid_never_falls_back_to_the_session`, `test_a_refusal_never_echoes_the_credential` |
| S7 | Scope escalation: a scoped credential reaches more than its scopes name, or a scope widens a role | 1, 2 | One scope language for keys and tokens (`server/scopes.py`): SMART v2 `system/` read scopes for the FHIR types served, Mendari's decide and outcome URIs. Effective permissions are the role's intersected with the scopes'; each route a scope can reach names its one scope, and a scoped principal gets `403 insufficient_scope` (with the `scope` it lacks) everywhere else, every other `/api` route and the dashboard included. A key's scopes, and a client's, are parsed strictly (a scope not granted, or one its role cannot use, is a `422`), and a stored scope that no longer parses refuses the credential. An access token gets what it asked for within what its client registered, and on every request that is narrowed again by the client's registration as it is then, so a token never outlives a narrowing. | `test_every_route_principal_role_and_scope_gets_what_it_should` (keys and tokens), `tests/test_scopes.py`, `test_a_scoped_key_reaches_only_what_its_scopes_name`, `test_a_scope_never_widens_a_role`, `test_the_scope_granted_is_what_was_asked_within_what_was_registered`, `test_a_token_reaches_only_what_its_scope_names` |
| S8 | A forged or replayed client assertion at `POST /auth/token` | 1, 2 | Off unless `MENDARI_BACKEND_SERVICES=on`, which refuses to start without sign-in and `MENDARI_PUBLIC_URL`. Only RS384 and ES384, only the `alg`, `kid` and `typ` header fields (no `jku`, `x5u`, `x5c`, `jwk` or `crit`: Mendari fetches no key), exactly one registered key for the `kid` and key type, `aud` exactly `{MENDARI_PUBLIC_URL}/auth/token` (never the Host header), `exp` required and at most five minutes ahead (30 s skew), `iss` = `sub`. Every check runs before the `jti` is claimed, the one write an assertion can cause, and the client lookup is the one read an unsigned request can cause. The claim is atomic across instances, per client, until the assertion expires. Every failure is one `invalid_client`; the reason is logged with the client's id only, never the assertion. | `test_every_assertion_that_does_not_authenticate_gets_one_answer_and_writes_nothing` (37 kinds, SQLite and Postgres), `test_a_replayed_assertion_is_refused_and_a_jti_is_per_client`, `test_refusals_are_logged_by_client_id_only`, `test_the_server_refuses_to_start_without_what_it_needs` |
| S9 | A stolen access token | 1, 2 | Tokens are opaque (`mat_…`), live five minutes with no refresh token, are stored as SHA-256 and sent only in the `Authorization` header (never a URL or form), and token answers are `no-store`. Each request reads the client's role, scopes, organization and revocation (one join), so revoking a client stops its tokens at once; turning Backend Services off stops every token. A token reaches only what its scopes name, in its client's organization. | `test_each_request_reads_the_client_as_it_is_now`, `test_a_token_acts_in_its_clients_organization_only`, `test_tokens_stop_working_when_backend_services_is_turned_off`, `test_an_expired_token_is_refused_and_purged` |
| S10 | Persistence: a stolen key or token registers a client (or key) that outlives it | 1 | Registering and revoking clients needs the people-only `keys` permission, so no key or token can, an old admin key included. Clients are `viewer` or `service`, with a public JWK Set only (a private or symmetric key is refused, never stored), and registering and revoking are chained (`client:<id>`, with the keys' ids and thumbprints). | `test_clients_are_managed_by_people_with_the_keys_permission_only`, `test_a_jwks_with_anything_but_public_signing_keys_is_refused`, `test_a_person_registers_a_client_and_the_chain_records_it` |
| S6 | A public logout deletes another kind of row (a pending sign-in, an EHR launch's session, a one-time claim such as an assertion's `jti`, which would let it be replayed) by a cookie value the caller chooses | 1 | Session-table rows are keyed by sha256(kind ‖ 0x00 ‖ value), and every take and delete is scoped to its kind; one-time claims (`smart_claim`) are a single `INSERT … ON CONFLICT`, atomic across instances. | `test_a_public_logout_deletes_only_its_own_kind_of_row`, `test_a_claim_is_atomic_across_connections` (SQLite and Postgres), `test_a_replayed_assertion_is_refused_and_a_jti_is_per_client` |
| S4 | A forged pack or publisher | 5 | Ed25519-signed deterministic archives, keys pinned on first use, and immutable versions. | `tests/test_archive.py`, `tests/test_hub_client.py` |
| T1 | The audit trail is edited after the fact | 6 | Every event is hash-chained, and `mendari audit verify` detects any change. PHI inputs live outside the chain, so retention can delete them without breaking it. | `tests/test_audit.py`, `tests/test_phi.py` |
| T2 | A pack's logic is swapped at a site | 5, 6 | The pack digest is recorded on every decision and deployment. A governance approval is bound to the digest. | `tests/test_governance.py` |
| R1 | Someone denies a review, an outcome or an approval they made | 1 | With sign-in on, the reviewer, reporter, outcome recorder (`recorded_by`) and approver are the signed-in principal, whatever the request body says. Each is chained. | `test_reviews_and_ratings_are_recorded_for_whoever_is_signed_in`, `test_an_outcome_is_recorded_for_whoever_sends_it` |
| T3 | Free text (possibly PHI) written for good into the chain and the FHIR export through a downstream outcome | 1, 2 | An outcome's `source` must be a system identifier (`^[A-Za-z0-9][A-Za-z0-9._:/@-]{0,99}$`) and its label one of the decision's question's labels (at most 200 characters, as for reviews); a refused label is not echoed. In FHIR the recorder is the agent and the source a `source.site`. | `tests/test_outcomes.py` |
| I1 | PHI leaks through storage | 6 | PHI mode `hash` stores no input. `encrypt` uses AES-256-GCM bound to the decision id, apart from the chain, with a retention purge. | `tests/test_phi.py` |
| I2 | PHI leaks to someone who shouldn't read it | 1 | Encrypted inputs open only for signed-in reviewers and admins, and every read is chained. Lists never carry inputs. | `test_signed_in_reviewers_read_inputs_and_each_read_is_chained` |
| I3 | PHI leaks into reports, errors or exports | all | Reports carry ids and metrics, never case text. Provider errors are stable codes without remote bodies. Shared and population reports suppress cells under 10. The FHIR audit export carries codes and hashes. | `tests/test_share.py`, `tests/test_omop.py`, `tests/test_audit_fhir.py` |
| I4 | One organization sees another's data | 1 | Tenancy lives in a context variable. The store filters every read and stamps every write. | `test_organizations_never_see_each_others_work` |
| I5 | Data goes to a model provider unexpectedly | 4 | Remote providers are off until configured. A pack declares the `state_fields` a remote provider may receive, and nothing else is sent. | `tests/test_jev_batching.py`, `tests/test_llm.py` |
| I6 | The browser leaks a session or page | 1 | HttpOnly, Secure cookies that say `SameSite=Lax` explicitly (so Chrome's two-minute exception for cookies without the attribute never applies). HSTS (two years) on every host but this machine. Headers on every response, with no page exempt: a CSP with each page's own inline scripts by hash only and nothing from another origin, `frame-ancestors 'none'`, nosniff, no referrer, COOP/COEP/CORP. The API reference (`/docs/reference`) is Swagger UI vendored at a pinned version, never loaded from a CDN, under a CSP with no inline script or style; it never calls Swagger's online validator. The public developer landing (`/docs`) is built once at startup from settings (never from a request's `Host`), under a CSP with no inline style, and with sign-in on shows nothing that differs with the packs installed: no pack, provider, count or record. | `tests/test_security_headers.py`, `tests/test_vendor.py`, `tests/browser/test_docs.py`, `tests/test_landing.py`, `tests/browser/test_landing.py`, `test_hsts_on_every_host_but_this_machine`, `test_cookies_of_a_sign_in_say_samesite_lax_explicitly`; ZAP |
| D1 | Oversized or slow upstream answers hold the server | 3 | One outbound client: allow-listed origins, no redirects, timeouts and size caps. | `tests/test_fhir_client.py` |
| D2 | Provider costs run away | 4 | Daily call budgets per provider type, visible in `/api/health`. | `test_daily_budget_is_enforced` (`tests/test_audit.py`) |
| D3 | A caller without a credential makes the server read large bodies | 1 | No request body is read before the sign-in check; routes read bodies with a cap (the token form 16 KiB, a search form 256 KiB), a chunked one only up to it. A credential in a form is refused by the route that reads it. | `test_no_body_is_read_before_the_sign_in_check`, `test_a_chunked_body_is_read_only_until_it_passes_the_limit`, `test_a_search_form_is_read_only_up_to_its_limit` |
| E1 | SSRF: making the engine call internal addresses | 3 | Every outbound call (FHIR, CQL, OIDC, PAS, webhook) goes through the allow-list. Webhooks must use https. | `tests/test_fhir_client.py`, `tests/test_monitoring.py` |
| E2 | A role does more than it may | 1 | A role table grants permissions, a matrix test covers every route for every principal kind, role and scope, and the dashboard hides what the server would refuse. Verifying and exporting the whole chain need `admin`. Machines are `viewer` or `service`. | `tests/test_auth.py`, browser tests |
| E3 | Automation beyond what the risk allows | runtime | Policy only lowers automation. Level 4 is never automated, and levels 2–3 only under a recorded, unexpired approval of that digest. | `tests/test_policy.py`, `tests/test_governance.py` |
| E4 | Injection (SQL, template, command) | all | SQL is parameterised everywhere (the one dynamic part, a schema name, is checked). No shell. Templates fill only FHIR ids into queries. | `tests/test_fhir_client.py`, `tests/test_omop.py`; ZAP active rules |
| E5 | A vulnerable or tampered dependency, action or image | all | `pip-audit` (Python lockfile, the tool itself locked) and `npm audit` (Hub site) in CI. Actions are pinned to commit SHAs and checkouts keep no credentials; images (CI, Dockerfile, compose) are pinned by digest; downloads are checked against a pinned sha256. The API reference's Swagger UI is vendored from npm, checked against its lockfile's integrity value and each file's sha256, and a Dependabot update fails CI until it is vendored again. The Docker image installs `uv.lock` exactly (`uv sync --frozen`), and the build backend is pinned. Dependabot proposes updates monthly, of versions at least 7 days old (security updates at once), with no Vercel preview for its branches. Release images are deployed by digest (`deploy/`). | CI job `security`; `tests/test_supply_chain.py`, `tests/test_vendor.py`; CI job `docker` |
| E6 | Cross-site request forgery: a page on another site (or a sibling subdomain, which is same-site) makes a signed-in browser act here: sign out, decide in an EHR launch, or open the review queue, which under PHI `encrypt` chains an `input.read` per input in the reader's name | 1 | Before anything else in the guard (no session lookup, no body read), a request that carries a Mendari cookie and no `Authorization` header, and in open mode every request, is checked (`server/origin.py`). With `Sec-Fetch-Site` `cross-site`, `same-site` or an unknown value, it reaches only `public` and `page` routes (from the route permissions, so there is no list to keep) and only with GET or HEAD: links to the dashboard, the API reference, the capability statement and the sign-in and launch callbacks work; a link to an API route does not. `none` (the address bar) passes to read only. Without Fetch Metadata, an `Origin` that is `null` or not the request's own host, `MENDARI_PUBLIC_URL` or one of `MENDARI_TRUSTED_ORIGINS` counts as cross-site. A request with neither is not from a browser (curl, ZAP, pilot-check) and passes. Refusals are a `403` (an OperationOutcome on FHIR routes) that echoes nothing. JSON routes also refuse non-JSON bodies (FastAPI >= 0.132), and no route grants a CORS preflight. | `tests/test_origin.py`: every route x 12 kinds of request x each mode, `test_a_refused_request_never_reaches_the_store_a_body_or_a_handler`, `test_a_link_to_the_review_queue_from_another_site_is_refused_and_nothing_is_chained`, `test_signing_out_from_another_site_is_refused`; browser suite (real Fetch Metadata) |

## Residual risks and assumptions

- **The deployment is the site's.** TLS termination, network placement, backups, the
  database's own access control and the PHI key's custody (a KMS or secret manager) belong to
  the deploying organization (`docs/deploying-with-phi.md`).
- **Open mode trusts its network.** Without sign-in the server is open. Production sits behind
  Vercel Authentication, and the sandbox listens on 127.0.0.1 only.
- **Clinical content** (pack criteria, rules, thresholds) is outside a security review. It
  needs clinician review and local validation, and every pack's card says so.
- **A CSP does not stop navigation.** A compromised script in a page could still navigate
  away carrying what it read. The vendored Swagger UI is protected by its pin, the integrity
  check and a review of each update (`scripts/vendor_docs_ui.py` lists the hosts a new bundle
  names), not by the CSP alone.
- **Synthetic data only** until the owner's go-ahead for real patients, after this review.
- **The token endpoint has no rate limit of its own yet** (Phase 4b). A failed assertion costs
  reading at most 16 KiB (a chunked body is read only that far), one indexed client lookup
  and, for a known client, one signature check; nothing is written or fetched. No other
  request body is read before the sign-in check. Until then it is unreachable behind Vercel Authentication, and Vercel's WAF is
  the place for a per-IP limit.
- **One database, one public URL.** Tokens and `jti` claims are rows in the deployment's
  database. Two deployments that share a database and a `MENDARI_PUBLIC_URL` (a preview
  pointed at production's database, say) accept each other's tokens and assertions. Give
  preview its own database, or keep Backend Services off there.
