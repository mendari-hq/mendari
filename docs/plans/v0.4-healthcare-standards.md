# v0.4 Healthcare standards: plan

> Written before the project was renamed from OpenHealth Hub to **Mendari** (2026-09-30).
> Names, commands and paths below are as they were: `openhealth` is now `mendari`,
> `OPENHEALTH_*` settings are `MENDARI_*` (the old names still work), and pack ids start with
> `mendari/`.

_Written 2026-09-29. The user approved every milestone from v0.4 to v1.0 in advance, and new
infrastructure where it is recommended ("Execute the full project roadmap", overnight run).
Status is tracked in `tasks/todo.md` and `docs/overnight-log.md`._

## Objective

Decision Packs run inside real EHR workflows through the standards those workflows use, and a site
can validate a pack on its own data exported in bulk:

- **US Core validation** of FHIR inputs;
- **audit export** as FHIR AuditEvent and Provenance;
- a **SMART on FHIR** EHR launch (OAuth 2 with PKCE and OpenID Connect) that opens the dashboard
  in the patient's context;
- **CDS Hooks** that fetch missing prefetch data from the EHR's FHIR server, under an allow-list;
- **Bulk FHIR** `$export` ingestion into local-validation datasets.

**Exit (from the roadmap):**
- the inbox and referral packs run from a SMART launch against the HAPI sandbox;
- Bulk export → `openhealth eval` works end to end.

## Context and constraints

- **FHIR today** (`standards/fhir.py`): declarative mappings (`fhir/mapping.yaml`) turn a Bundle,
  a resource or a CDS Hooks prefetch into pack input, and a decision into a `Task`.
- **CDS Hooks today** (`standards/cds_hooks.py`): prefetch only. The service never calls a
  caller-supplied URL, which avoids SSRF (architecture, "Trust boundaries").
- **Sandbox:** `docker compose up` runs HAPI FHIR 8.12 and the engine. Only the inbox is seeded
  into FHIR (Patients and Communications).
- **Production** is Vercel behind Vercel Authentication, with no auth of its own. That stays true in
  v0.4: every new capability is **off until configured**, and no production environment variable
  changes. v0.6 brings OIDC login with roles.
- **Rules that hold:** no real PHI; providers raise only `ProviderError`; policy only lowers
  automation; reports carry ids, never case text. Pack content, digests and derived artifacts do
  not change in this milestone.

## Approach (one PR each, in order)

### 1. US Core validation of FHIR inputs
- **`standards/us_core.py`**, a declarative subset of **US Core 6.1.0** for the resources the packs
  read: Patient, Condition (problems and encounter diagnoses), Observation (laboratory and the
  base profile), MedicationRequest, MedicationStatement (not in US Core 6: base R4 checks only),
  ServiceRequest, DocumentReference, DiagnosticReport (report and note), Coverage, Encounter,
  Communication (base R4).
  - **What each profile checks:**
    - required elements (min cardinality 1);
    - required bindings (fixed code systems such as AdministrativeGender, or the profile's
      category codes);
    - `reference` targets for `subject` and `patient`;
    - the profile's key invariants that can be checked without a terminology server (for
      example us-core-6: "Condition.code or Condition.category").
  - **How a profile is picked:** by `meta.profile` when present, otherwise by resource type (and
    Observation category).
- **Result:** an `OperationOutcome`-shaped list of issues: severity, code, FHIRPath `expression`,
  and a diagnostic with no patient values.
- **Where it runs:** every FHIR entry point (`/fhir/decide`, CDS Hooks, SMART, Bulk).
  - A server setting `OPENHEALTH_FHIR_VALIDATION` = `off` | `warn` (default) | `enforce`.
    - **warn:** decide as today and return the issues in `validation`, plus a count in the audit
      record's metadata.
    - **enforce:** a required-element error blocks the input before any provider sees it,
      exactly like a JSON Schema failure today (`BLOCK`, reason "input does not conform to
      US Core"). A block is the only way enforcement can change an outcome, and it lowers
      automation, never raises it.
- **Conformance in CI:** a new `fhir-conformance` job runs the official HL7 FHIR validator
  (pinned `validator_cli.jar`, checksum verified) with `hl7.fhir.us.core#6.1.0`. It checks:
  - every resource the sandbox generates;
  - the example Bundles in `tests/fixtures`;
  - the AuditEvent and Provenance exports (PR 2).

  An error fails the job. This keeps the in-process subset honest against the real profiles.

### 2. Audit export as AuditEvent and Provenance
- **One decision:** `GET /api/audit/{id}/fhir` returns a `collection` Bundle with:
  - an **AuditEvent** per chained event (`decision.created`, `review.resolved`,
    `outcome.recorded`, `feedback.*`):
    - `type` is audit-event-type `rest`, with a `subtype` from an OpenHealth CodeSystem that
      names the event (the DICOM event codes describe queries and exports, not decisions);
    - `agent`: the engine as a Device (pack id and version, provider variants) and, for reviews,
      the reviewer as `who.display` / `altId`;
    - `entity`: the decision identifier;
    - the chain's `prev_hash` and `hash` as `entity.detail`, so the tamper evidence survives
      export;
  - one **Provenance** whose `target` is the decision's `Task` (by identifier):
    - `activity` iso-21089-lifecycle `originate` for the decision, `verify` for a confirmed
      review and `amend` for an override;
    - agents: the engine (author, a Device) and the reviewer (verifier);
    - `entity`: the input as a `source`, by hash only.
- **A range:** `GET /api/audit/export/fhir?pack_id=&since=&until=` streams
  `application/fhir+ndjson`.
- **CLI:** `openhealth audit export --format fhir-ndjson`.
- **Privacy:** no case text, as in reports; stored inputs are referred to by hash.

### 3. Sandbox: referral cases in FHIR
- `openhealth sandbox seed --pack openhealth/referral-router` loads the referral local-site cases
  as US Core Patients, referral ServiceRequests (SNOMED 3457005), DocumentReferences,
  DiagnosticReports and laboratory Observations, tagged as today.
- A round-trip test: FHIR → mapping → input equals the dataset's input, for every case. This
  is the basis of the SMART and Bulk exits.

### 4. CDS Hooks that fetch
- When a prefetch key is missing and the request carries `fhirServer` and `fhirAuthorization`,
  the service runs the pack's own prefetch template for that key, with `{{context.*}}` filled,
  against `fhirServer` using the bearer token.
- **Allow-list:** `OPENHEALTH_FHIR_ALLOWED_SERVERS`, exact origins, comma-separated. Empty by
  default, so fetching stays off, as today.
  - `https` only, except `http://localhost` and `http://<compose service>`, which must be listed
    explicitly.
  - No redirects, a 10 s timeout, a 5 MB response cap, JSON only, and FHIR errors surfaced as
    `FhirError` without remote bodies.
  - Tokens are never logged or stored.
- The architecture's trust-boundary section is updated.

### 5. SMART on FHIR EHR launch
- **Endpoints:**
  - `/smart/launch?iss=&launch=` reads `iss/.well-known/smart-configuration`. `iss` must be on
    the same allow-list.
  - It redirects to `authorize` with PKCE S256, `state`, `aud=iss` and the scopes
    `launch openid fhirUser patient/*.rs` (SMART v2) or the v1 `.read` equivalents.
  - `/smart/callback` checks `state`, exchanges the code, and validates the `id_token` (RS256
    or ES384 through the server's JWKS, plus `iss`, `aud`, `exp` and `nonce`). It keeps
    `patient`, `encounter` and `fhirUser`.
- **Session:** an opaque random id in an `HttpOnly; Secure; SameSite=Lax` cookie.
  - The access token lives server-side in a new `smart_sessions` table (SQLite and Postgres)
    with its expiry.
  - Sessions expire with the token and are deleted on logout.
  - No refresh tokens are requested.
- **Dashboard:** a patient banner (name initials, age band, encounter) and a "This patient" view.
  - It fetches the pack's focus resources for the patient (inbox: in-progress Communications;
    referral: referral ServiceRequests) with the session's token, through the same allow-list
    client.
  - It runs each one through `/fhir/decide`, and links to the audit record.
- **Client registration:** `OPENHEALTH_SMART_CLIENT_ID` (public client with PKCE by default;
  `OPENHEALTH_SMART_CLIENT_SECRET` for a confidential one). Unset, so SMART is off.
- **Sandbox:** `smartonfhir/smart-launcher-v2` (pinned) in `docker-compose.yml`, in front of
  HAPI. Its launch parameter can skip login and consent, which makes the whole flow scriptable
  over HTTP.
- **Dependency:** `pyjwt[crypto]` (pinned) to verify id_tokens, and to sign the backend-services
  assertion in PR 6.

### 6. Bulk FHIR `$export` into local-validation datasets
- **`openhealth bulk export`:**
  - `--fhir URL`, with `--group ID` or patient-level export, plus `--type`, `--since` and
    `--out DIR`;
  - kick-off with `Prefer: respond-async`, then polling that honours `Retry-After`, with
    exponential backoff and a deadline;
  - downloads NDJSON files and verifies their counts;
  - **auth:** none (sandbox), or SMART Backend Services, meaning client credentials with a
    `private_key_jwt` assertion signed with a key from `OPENHEALTH_BULK_PRIVATE_KEY`;
  - the same allow-list applies.
- **`openhealth bulk dataset`:**
  - builds one case per focus resource through the pack's FHIR mapping, writing the local
    dataset format (`{"id", "input", "labels"}`);
  - joins labels from a site-provided file keyed by a FHIR identifier system
    (`--labels FILE --key-system URI`), because ground truth lives in chart review, not in the
    EHR;
  - cases without a label are kept for coverage but excluded from accuracy, as today.
- **Sandbox:** HAPI with bulk export enabled.

### 7. End-to-end exit checks
- A new CI job, `sandbox-e2e`, brings up the compose stack (HAPI, the launcher, the engine),
  then:
  1. seeds the inbox and referral cases;
  2. runs a scripted SMART launch for each pack through the launcher and decides the patient's
     focus resources through the engine's SMART endpoints;
  3. runs `bulk export` → `bulk dataset` → `openhealth eval`, and checks that the metrics equal
     an evaluation of the same cases from the example file.
- Docs: README (SMART, CDS fetch, Bulk, validation settings), architecture trust boundaries,
  the roadmap scorecard's FHIR row, and `tasks/todo.md`.

## Verification

- [ ] The US Core subset: a test per rule (valid and invalid), and the HL7 validator agrees on
      the fixtures (no resource we accept as valid is an error for the validator).
- [ ] `enforce` blocks before providers run, and `warn` never changes an outcome (property test
      over the behaviour-test cases).
- [ ] AuditEvent and Provenance validate against base R4 with the HL7 validator. The exported
      hashes re-verify the chain.
- [ ] CDS fetch: allow-listed fetch works; a non-listed origin, a redirect, an oversized
      response and a non-JSON response each fail closed with a `FhirError`, and the token
      never appears in logs or errors.
- [ ] SMART:
  - [ ] state mismatch, nonce mismatch, a bad signature, expiry and a wrong `aud` are each
        rejected (tests with an in-process authorization server);
  - [ ] the cookie flags are set;
  - [ ] logout deletes the session;
  - [ ] the sandbox launch works for inbox and referral.
- [ ] Bulk: kick-off, 202 polling with `Retry-After`, error OperationOutcome and deadline
      (tests with a fake server). Sandbox end to end: metrics match.
- [ ] No new setting changes behaviour when unset. The full suite, the browser suite and the
      reference-pack reproducibility job stay green.

## Risks

- **US Core subset drift from the real profiles.** Mitigation: the HL7 validator job over the
  same fixtures.
- **SSRF through `iss`, `fhirServer` or bulk URLs.** Mitigation: one allow-list client used by
  every outbound FHIR call, with no redirects and a size cap. It is off by default.
- **Token leakage.** Mitigation: tokens only server-side, never in URLs after the callback,
  never logged; the cookie is opaque.
- **CI time.** HAPI and the launcher take about a minute to start. Mitigation: one e2e job,
  cached images, run in parallel with the others.
- **Serverless state.** SMART sessions live in the database, not in memory, so they work on
  Vercel.
