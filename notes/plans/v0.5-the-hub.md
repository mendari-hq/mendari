## Objective

Decision Packs become distributable, like models on Hugging Face:
- **packaged** as an immutable, signed archive;
- **published** to a registry with namespaces and publisher types;
- **found** by search;
- **pulled and verified** by anyone with `pip install openhealth`.

Sites share evaluation results (metrics only) to compare with each other.

**Exit (from the roadmap):**
- the five packs are published;
- on a clean machine, `pip install openhealth && openhealth pull openhealth/referral-router`
  works.

## Context and constraints

- **Packs today** load from local paths (`core/registry.py`: `OPENHEALTH_PACKS_PATH` and the
  bundled packs). Each already has a content digest (`core/pack.py`), and `Decision.from_hub`
  resolves `namespace/name[@version]` locally.
- **Sizes:** the five packs are 0.6–2.1 MB uncompressed, so archives fit comfortably in Postgres.
- **Production** is Vercel behind Vercel Authentication. A public registry and a PyPI release
  are public, hard-to-undo steps: they need production signing keys and credentials, and they
  make the project's content public. This plan builds and verifies everything locally and in
  CI. **Going live is left to the user** (logged as blocked with what's needed), together with
  the v1.0 launch.

## Approach (one PR each)

### 1. Pack archives and signatures
- **`openhealth pack build <path>`** writes `<namespace>-<name>-<version>.ohpack`: a deterministic
  gzip tar (sorted entries, fixed mtime/uid/gid/mode, gzip mtime 0). The same pack always gives
  the same bytes, and so the same archive digest. The archive holds:
  - `pack/…`: the pack directory;
  - `openhealth-pack.json`: the format version, pack id, version, the pack's content digest, and
    every file with its SHA-256 and size;
  - `openhealth-pack.sig`: an **Ed25519** signature over the canonical manifest bytes, with the
    key id.
- **`openhealth keys generate`** creates a publisher key pair (PEM, private key 0600).
- **`openhealth pack verify <archive> --key <public.pem>`** checks:
  - every file hash;
  - the recomputed pack digest;
  - the signature.

  Archives are extracted safely: no absolute paths, no `..`, no links, and a size cap.
- `cryptography` (already a dependency, through `pyjwt[crypto]`) provides Ed25519, so there is
  no new dependency.

### 2. Registry service
- **`openhealth.registry`** is a FastAPI app on the same database layer as the audit store:
  SQLite locally, Postgres (Neon) deployed. `core/db.py` is extracted from `core/audit.py` as a
  pure move, checked line for line.
- **Namespaces** have a publisher type (community / verified / institutional) and registered
  Ed25519 public keys. Publisher tokens are stored hashed. An admin token (from the environment)
  creates namespaces, sets the publisher type after verification, and issues publisher tokens.
- **Pack versions are immutable.** `PUT /v1/packs/{ns}/{name}/{version}` takes an archive. It is
  accepted only if:
  - the namespace and the manifest match;
  - the signature verifies with a key of that namespace;
  - the pack validates;
  - that version does not exist yet (otherwise 409).

  Stored with each version: the archive, its digest, the Decision Card, the benchmark summary,
  the provider leaderboard, the risk level and the standards (FHIR, CDS Hooks).
- **Reads:**
  - `GET /v1/packs/{ns}/{name}` (versions), `…/{version}` (metadata), `…/{version}/archive`;
  - `GET /v1/search?q=&task=&risk=&standard=&publisher_type=`;
  - `GET /v1/namespaces/{ns}` (publisher and keys).
- **Archive storage** is a small interface: a database backend now, with Vercel Blob as a later
  backend when sizes call for it.
- `openhealth registry serve`, and a `registry` service in `docker-compose.yml`.

### 3. CLI and `Decision.from_hub`
- **`openhealth login --registry URL --token T`** stores credentials in
  `~/.config/openhealth/credentials.json` (0600).
- **`openhealth push <pack>`** builds, signs with the publisher key and uploads.
- **`openhealth pull ns/name[@version]`** downloads to `~/.cache/openhealth/packs/…` and verifies
  (archive digest from the registry, file hashes, pack digest, signature with the namespace's
  key). Keys are pinned on first use, and a changed key is refused unless the user accepts it.
- **`openhealth search`**.
- **`Decision.from_hub`** falls back to the registry (`OPENHEALTH_REGISTRY_URL`) when the pack is
  not local, and uses the verified cache.

### 4. Shareable local-validation reports
- **`openhealth eval … --share`** uploads the report's metrics (reports already hold no case
  text) under a site pseudonym chosen by the site.
- **`GET /v1/packs/{ns}/{name}/reports`** returns site-to-site comparisons against the benchmark:
  accuracy, false automation, calibration and n per site.

### 5. Hub website (Next.js)
- **`hub/`** is a Next.js (App Router, TypeScript) site that reads the registry API:
  - home and search, with filters for task, risk level, standard and publisher type;
  - pack pages: Decision Card, versions, benchmarks and leaderboard, FHIR mapping, CDS Hooks,
    and site reports;
  - publisher pages.
- A CI job runs lint, typecheck and build, plus a Playwright smoke test against a local registry
  with the five packs.

### 6. End to end
- A CI job builds the wheel and starts a registry. It pushes the five packs, then in a **clean
  virtual environment**:

  ```
  pip install <wheel> && openhealth pull openhealth/referral-router && openhealth test openhealth/referral-router
  ```

- Docs: README "The Hub", the roadmap scorecard, and the architecture's trust boundaries.

## Verification
- [ ] Archives are byte-reproducible (built twice, same digest).
- [ ] A tampered file, manifest or signature fails verification, and so does a key from another
      namespace.
- [ ] Extraction refuses traversal, links and oversize files.
- [ ] The registry:
  - [ ] refuses re-publishing a version, publishing into another namespace, a bad signature and
        an invalid pack;
  - [ ] stores tokens hashed;
  - [ ] search filters work;
  - [ ] runs on both backends.
- [ ] Pull verifies everything, pins keys, and refuses a changed key.
- [ ] `from_hub` resolves remote packs through the cache.
- [ ] The e2e job: five packs pushed, then a clean-venv install, pull and behaviour tests.
- [ ] Shared reports carry metrics only (checked against case text).
- [ ] Hub: build, typecheck, and a smoke test of search and a pack page.

## Risks
- **Supply chain (a malicious or tampered pack).** Mitigations:
  - signatures, per-namespace keys, pinned keys and immutable versions;
  - verification before a pack is used;
  - safe extraction.
- **Scope of the website.** Keep it read-only and generated from the API.
- **Going public.** Nothing is deployed publicly by this plan; that's the user's decision (log).
