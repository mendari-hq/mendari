# Threat model

_Mendari engine, dashboard and registry, as of Phase 4b (2026-10-02), with community packs
(2026-10-04), registry packs on the community engine (LP-16, 2026-10-08), and a registry that
shows only what it checked, with recalls and the cap on pulled packs (LP-18, 2026-10-17), and CDS
clients' own signed tokens, with open mode's CDS Hooks on this machine only and CORS for their registered origins (LP-23b and LP-23c, 2026-10-18), and the scoreboard: its results store, signed results and the hidden-set scoreboard (LP-17, 2026-11-06), and the EHR pilot's reads and answers: recorded abstentions, data coverage, card feedback, linked reads and site code maps (LP-23, 2026-11-06). Reviewed before the public launch; update it with any change to a trust boundary. The checks named here run in CI.
Ids are stable: a new threat takes the next number in its letter, and a removed one leaves a
gap. The packet for the external review is [`review-packet.md`](review-packet.md)._

## What we protect

| Asset | Why it matters |
|---|---|
| Decision inputs (messages, records; PHI in a real deployment) | Patient privacy. |
| Decisions, reviews, outcomes and the audit hash chain | Clinical accountability: what was decided, by what, and who changed it. |
| Governance approvals | They lift the automation cap at risk levels 2–3. |
| Sessions, API keys, OIDC and SMART tokens | Whoever holds them acts as a clinician, an integration or an admin. |
| Provider credentials (Jev, LLM gateway keys) | Cost, and a channel to send data out. |
| Pack integrity (signed archives, publisher keys) | A tampered pack changes clinical logic at every site that pulls it. |
| PHI encryption key | It opens every stored input. |
| The grading signing key | Whoever holds it signs scoreboard results as Mendari's. |

## Trust boundaries

1. **Browser ↔ engine:** the dashboard and the API.
2. **EHR ↔ engine:** CDS Hooks, SMART launch, DTR and FHIR decide.
3. **Engine → outside servers:** FHIR servers, the CQL engine, the identity provider, the payer
   and alert webhooks, and the registries a server reads its pulled packs' recalls from.
4. **Engine → model providers:** Jev, and LLMs through a gateway.
5. **Registry ↔ clients:** publishing, pulling and recalling packs, and the Hub website, which
   shows the registry's packs to anyone.
6. **Engine ↔ database:** SQLite or Postgres.
7. **Contributors ↔ repository:** community packs arrive by pull request from forks, and only
   the owner's merge puts one in `community-packs/` ([ADR-0007](../decisions/ADR-0007-community-packs-by-pull-request.md)).

## Pack content

What a Decision Pack can set, which packs the deployment owns, and what a pack can and cannot do
with what it sets (LP-16,
[ADR-0009](../decisions/ADR-0009-bounded-evaluation-for-packs-the-deployment-does-not-own.md)).
Each limit names the row above that holds it; each thing a pack can do names the row that bounds
it, or why it is left as it is.

### Inputs

A pack is a directory, or a signed archive of one (S4). Mendari reads it as data (YAML, JSON and
text): nothing in it is imported or run as Python, and a `cql` variant's library runs on the
deployment's CQL engine. Its digest covers every file but those under `evals/`, any
`DECISION_CARD.md`, and hidden entries and `__pycache__` (S15); a file it decides or tests with
is read only if the digest covers it, and only as hashed (T2, E9). What a pack sets:

| Input | What it sets | Checked |
|---|---|---|
| `pack.yaml` | The manifest: `spec_version`, id, version, name, summary, `license`, publisher, risk level, card, `code_systems`, the questions (their instructions and criteria are the prompt its model variants send), the provider slots and their variants, `audit.store_input`, `guard`, `cds_hooks` and `evaluation` | At load, as a closed model but for the variant keys (`core/spec.py` `PackManifest`) |
| `policy` | Thresholds, rules, label policies and `automation_requires`: inline, or in a file it names | At load; policy only lowers automation (E3) |
| `inputs.schema` | The JSON Schema every input is checked against | At load (`core/input_schema.py`): self-contained (E9); for a pack the deployment does not own, its keywords and the caps (D8); for an owned one, the expansion bounds (D10) |
| `inputs.fhir` | The FHIR mapping: how a record becomes an input, and the Task a decision writes; in spec 0.3 also `[system=…]` predicates, fallback `paths`, `follow` (a path of the field's own type read in place, LP-23k), `attachment_text`, `code_sets` and the `code_set` selector (for `focus_where` too, LP-23k), list `resources` and `medication_period` (LP-23g) | At load, that it is a file the digest covers (E9); its content at load for a pack the deployment does not own, for an owned one where it is used, and by `mendari validate`. ### Trust boundary

Whether the deployment owns a pack decides most of what follows. It is read from where the pack
was found and the digest `load_pack` hashed, never from a registry's record or a marker file; the
manifest can only give ownership up, by an id in `community/` (`core/origin.py` `bounded`, read
as `Pack.bounded`; S15):

- **Owned:** the reference packs this release bundles (`maintained`); an operator's own packs
  (`local`: in `MENDARI_PACKS_PATH`, or a path given on the command line), a copy of a pulled
  pack included, which is how an operator says it trusts one; and a pack pulled from a registry
  whose digest is one of the bundled reference packs', which is that pack. Installing an owned
  pack means trusting its author, as with any plugin.
- **Not owned:** a community pack (in `community-packs/`, or any pack whose id is in
  `community/`, wherever it was loaded from) and every other pack pulled from a registry
  (`hub`), and a version in an organization's pack store (`store`, LP-20e). These run on the
  community engine (D8), and
  what only warns for an owned pack refuses them at load.

A community pack recommends and never automates, wherever it was loaded from (E10). One in
`community-packs/` is held further, or it is not served (and CI refuses it): its default
variants are local, it is at most risk level 1 and it keeps only a hash of its inputs; and it is
served only with `MENDARI_COMMUNITY_PACKS=on` (E10). A pack with a `community/` id loaded from
anywhere else (`MENDARI_PACKS_PATH`, a path, a registry) is not held to these three. Every surface labels a community pack "Community · not clinically reviewed" (S13); the API, the
dashboard and the SMART patient view label every pack by its origin, and the Decision Card names
the source only of a maintained or community pack. A pack from
outside comes in across boundary 5 (a registry) or 7 (a pull request) above, and every pack
reaches out through 3 (FHIR servers, the CQL engine) and 4 (model providers), only at addresses
the deployment sets or allows (E1, E8).

### What a pack can do

- **An owned pack chooses what its model calls send and ask for.** A `jev` or `llm` variant
  without `state_fields` sends the whole input. A pinned `model` is used: an `llm` variant's
  wins over `LLM_MODEL`, and a `jev` variant's applies where the deployment sets no `JEV_MODEL`.
  It may ask for up to 32,000 tokens, an LLM timeout of up to 120 s (Jev 10 s) and any
  `reasoning_effort`, each call within the decision's deadline (D9). This is the operator's
  choice (I5); a pack the deployment does not own can do none of it (I5, E10).
  `test_a_registry_packs_remote_variant_needs_state_fields`,
  `test_a_registry_packs_pinned_model_gives_way_to_the_deployments`.
- **Any pack sets its own Jev price.** `cost_per_1k_input_tokens_usd` (finite and at most $1,
  since LP-21g, or null for unknown) sets the `cost_usd` recorded on its decisions, summed in the
  usage ledger and shown on the dashboard and in reports, a pack the deployment does not own
  included. It changes what is recorded, not what is called: the daily budgets and
  quotas count calls (D2). A pack from a store does not: its recorded cost is the deployment's
  price (LP-20e). Residual for a pack from a registry (`tasks/todo.md`, LP-16 conflict 24).
  `test_jev_request_is_minimal_and_typed`, `test_a_jev_call_without_a_price_is_unknown_never_zero`,
  `test_a_jev_price_is_finite_and_at_most_a_dollar_per_thousand_tokens`.
- **Any pack turns batching off or sets a temperature.** A model variant with `batch: false` is
  asked in a call of its own instead of sharing one with the decision's other questions, so a
  decision makes more calls, each counted against the budgets and quotas (D2) and made within
  the deadline (D9). An `llm` variant's `temperature` (0 to 2) is sent as the pack sets it. A
  pack from a registry keeps both, and a pack from a store keeps neither (LP-20e). Residual for
  a pack from a registry (conflict 24).
  `test_a_variant_can_opt_out_of_batching`.
- **A pack from a registry is chosen for as an owned pack is.** The deployment's unscoped
  `MENDARI_PROVIDERS` settings (`slot=variant`) apply to it. So do the Jev defaults while Jev is
  set up: they are keyed by pack id (`JEV_DEFAULTS`), so a pack from a registry with a reference
  pack's id at another version gets them where it has the same slots and variants. And
  `POST /api/packs/{namespace}/{name}/evals` runs any variant of it that a caller with the
  `evaluate` permission names, a remote one on up to 200 cases. A community pack, by contrast,
  takes only the settings that name it, and runs a remote variant only where named (E10). Residual
  (conflict 24), for a pack from a registry; a pack from a store, as a community pack, takes only
  the settings that name it (LP-20e). `test_unscoped_provider_settings_never_reach_a_community_pack`,
  `test_a_store_pack_does_not_set_its_own_cost_batching_or_temperature`.
- **A pack from a registry automates only once its organization approves it.** Served, it
  never automates until its organization approves its exact digest, at any risk level, and its
  own rules' BLOCK goes to a person until then; a recall recorded at pull or read by a running
  server, and a registry not read for a day, hold it the same way, approved or not (E12).
  Approved, it automates as an owned pack does: by its own thresholds at risk levels 0 and 1, at
  levels 2 and 3 only under an approval of its digest too, and never at level 4 (E3). Its risk
  level, for policy, is what its publisher declares; a registry reviewer's review shows whether
  it found the same (S18) and changes nothing here. Pulling it is the operator's choice
  (ADR-0009); only a community pack is held to recommending (E10).
  `test_a_pulled_pack_never_automates_before_its_digest_is_approved`,
  `test_a_running_server_stops_automating_a_pack_its_registry_recalls`.
- **An owned pack runs its patterns on `re`.** Its rules' and input schema's patterns run with
  no time limit, so one that backtracks stalls the worker that runs it while holding the
  interpreter (a crafted 10,000-character message to the inbox pack holds it for about 0.55 s).
  Accepted (ADR-0009, and the residual risks below). Its schema's shape is bounded at load (D10);
  a pack the deployment does not own runs on RE2 within a budget (D8).
  `test_owned_packs_stay_on_re`, `test_health_answers_within_its_bound_with_a_pathological_pack_loaded`.
- **An owned pack's content problems only warn.** A variant or member its provider's closed
  config refuses (a key nothing reads, a value out of range, a pack file the provider cannot
  use), a prefetch template that is not a relative read or search, and a card summary
  placeholder that is not bare: the pack loads with them as `Pack.warnings` (`mendari list`, the
  start-up log, `/api/health` `pack_warnings`) and decides as it did before LP-16, each variant
  building, or failing, as it did, but a Jev variant priced above $1 per 1,000 input tokens:
  LP-21g bounded the price, so it now fails when it is built. A Task text placeholder that is not bare is not warned of,
  and renders as before. `mendari validate` refuses all of them, and the prefetch still reads
  only from the EHR's FHIR server (E1). A pack the deployment does not own is refused for any
  of them (E1, E4, E8). Conflicts 17 and 21: making owned packs refuse is a one-line change, for
  the owner. `test_an_owned_packs_unread_key_warns_and_it_still_serves`,
  `test_a_broken_non_default_variant_is_refused_for_a_registry_pack_and_warned_for_an_owned_one`,
  `test_a_prefetch_template_must_be_a_relative_read_or_search`,
  `test_a_wording_template_takes_bare_placeholders_only`.
- **A pack's tests, datasets and attestations are its publisher's word.** Loading, a registry's
  publish and `mendari pull` check only that its tests and datasets are files the digest covers;
  `mendari validate` checks their inputs against the schema and their labels against the
  questions, and loading does not (conflict 17). Its benchmark, leaderboard and card are outside
  the digest, so they change without changing it. `community-check` evaluates a community pack
  again and refuses a benchmark or card that differs. A registry never reads or shows the ones
  a pack uploads: it renders the card itself from the files the digest covers, and its only
  figure is its own regression check on the pack's test set, labelled the publisher's own and
  never a ranking (S18). Where the engine serves a pulled pack it shows the registry's card and
  no uploaded benchmark or leaderboard, and neither its monitor nor its evaluations compare with
  the benchmark the pack carries (S18). None of them is read to decide (E9).
  `test_a_forged_card_benchmark_and_leaderboard_show_only_what_the_registry_rendered`,
  `test_a_pulled_packs_uploaded_benchmark_is_never_compared_or_monitored_against`.
- **A pack's slow decisions can keep health waiting.** `/api/health`, and the sign-in check that
  runs before every request, use the same thread pool as the decide routes (AnyIO's default, 40
  threads), and a decision waiting on remote providers holds its thread until they answer or
  its deadline passes (`MENDARI_DECISION_DEADLINE_S`, 120 s unless set; D9). Forty such
  decisions at once make health, and every other request, wait for a thread. Health itself does
  no pack work (D7). Residual (conflict 23), not in LP-16.

### What a pack cannot do

Whatever it says, and whoever wrote it, a pack cannot:

- **Pass for another pack or another origin.** Its origin is where it was found, and every
  surface labels it by origin; a community pack's id is `community/<name>`, never a maintained
  pack's, and its FHIR systems live under its own url (S13). A pack from a registry keeps the
  maintained engine only with a reference pack's digest (S15), and one with a reference pack's
  id, a version that ties its and other files is refused at load, publish and pull (S16).
- **Change what it decides behind its digest.** Every file it decides with is in its digest and
  read as hashed, so a file edited after the load is refused, never used, and a governance
  approval is bound to the digest (T2). It reads nothing outside its directory or its digest: no
  link out of the pack, no hidden entry, nothing in `evals/` on the decide path, and no `$ref` to
  a URL or a local file (E9).
- **Change another pack's logic.** Its CQL library goes to the shared engine under names that
  end in a hash of its pack id and text, so it cannot replace or shadow another pack's (T4).
- **Stop the server.** Whatever its content, a pack that fails to load or build is listed
  under `/api/health` `invalid` and every other pack is served, and health builds no pack in the
  request (D7). A pack the deployment does not own runs its patterns on RE2, within caps and a
  budget of one second of CPU per decision, so about 3.5 s at worst (D8); a decision's remote
  calls stop at its deadline, which a pack cannot set (D9). An owned pack's input schema is
  bounded at load (D10), but its patterns run on `re` with no time limit, so one that
  backtracks can stall its instance (above, and the residual risks).
- **Choose where its data goes, or with which credentials.** The variables a remote provider
  reads its endpoint, model and key from are fixed in the code and are the deployment's, a
  variant that names one is refused at load, and every call goes to the deployment's endpoints
  with its keys (E8); with `MENDARI_PROVIDER_ALLOWED_ORIGINS` set, a Jev or LLM call goes
  only to the origins it lists (E1, I5), and a `cql` call goes only to an origin on the FHIR
  allow-list, set or not (E1). A prefetch read stays on the EHR's FHIR server and fills in FHIR ids only (E1, E4), and its
  FHIR mapping fetches nothing itself: a `follow` or an attachment's `url` resolves inside the
  record it is given, or to nothing. What the record lacks, a CDS hook or the SMART launch's
  decide reads from the request's `fhirServer` only, under its base, at most 50 notes and 50
  followed references a decision and 100 reads a request, of at most 2 MiB each, inside the
  decision's deadline (E1, D14).
- **Inject through its wording.** A wording template names only `{recommendation}`,
  `{priority}` and the pack's questions, and in a pack the deployment does not own each is a
  bare name (E4).
- **Automate beyond its risk level.** Policy only lowers automation: level 4 is never automated,
  and levels 2 and 3 only under an approval of the pack's digest (E3).
- **Choose its model, the length of its answers, its timeouts or its reasoning effort, or send
  a model more than it names, if the deployment does not own it.** Its model is the
  deployment's, its `max_tokens` and `timeout_ms` are held to the provider defaults and a
  `reasoning_effort` above `low` is dropped (E10), every model variant and member names its
  `state_fields` (I5), and its configs are checked at load first (E8). Its questions' text, sent
  with every call, is its own, up to the provider's request limit (LLM 100,000 characters, Jev
  80,000).
- **Automate, block by a rule of its own, or call a model unasked, if it is a community pack.**
  It recommends and a person confirms every decision on an input that is not rejected, a rule of
  its own never blocks, and it runs a remote variant only where the deployment names it (E10).
  An input its schema rejects is still a final `BLOCK` (`input rejected`), as for any pack, so
  its schema (a `not` with a `pattern`, say) can refuse cases no person sees.

## Residual risks and assumptions

- **The patterns of the packs a deployment owns run on `re` with no time limit** (those of a
  pack it does not own, a community pack or one pulled from a registry, on RE2: D8, S15). Their
  input schemas are bounded at load (D10), so a schema's shape cannot multiply the work of
  checking an input; a pattern in it still runs on `re`.
  Installing a pack means trusting its author, as with any plugin. Rules patterns, input-schema
  `pattern`s and `patternProperties` keys are compiled at load (`core/patterns.py`: valid under
  `re`, at most 2,000 characters, at most 500 per pack), but a pattern that backtracks (`(a+)+$`
  takes seconds on 27 characters, doubling with each more) can slow or stall the worker that
  runs it, holding the interpreter while it does; compiling a large case-ignored class at load
  also costs CPU (a pack at the caps can add seconds to a start). The shipped packs are the
  owner's and reviewed; accepted with ADR-0009, a crafted 10,000-character message to the inbox
  pack can hold the interpreter for about 0.55 s on `re`, stalling its instance (the rate limits
  bound how often). Community packs are read by the owner before merge, and the patterns of
  every pack the deployment does not own run on RE2, which never backtracks, on texts of at most
  10,000 characters (D8), with the settings that multiply that work capped at load
  (`core/caps.py`, their size together included) and a time budget of one second of CPU per
  decision for their patterns and schema checks (D8), in the server's process (no isolated
  worker process: ADR-0009). A local copy of a pulled pack (in `MENDARI_PACKS_PATH`) is owned:
  it runs on `re`, as the operator's own. A time limit inside the `regex` module was tried for
  every pack and dropped (it could not match `re`'s semantics exactly, and its clock was the
  process's, not the thread's).
- **The deployment is the site's.** TLS termination, network placement, backups, the
  database's own access control and the PHI key's custody (a KMS or secret manager) belong to
  the deploying organization (`docs/deploying-with-phi.md`).
- **Open mode trusts its network.** Without sign-in the server is open. Production has sign-in
  on and sits behind Vercel Authentication until the launch, and the sandbox listens on
  127.0.0.1 only. Its CDS Hooks services alone answer this machine only (E16), since an EHR is
  what reaches them over a network; the rest of open mode answers any host.
- **An EHR launch trusts the EHR's sign-in.** A launch is a principal of its registered
  organization (E7) on the strength of the id_token the EHR signs: a site registers only an
  EHR whose sign-in it trusts, and one FHIR base for one organization (an EHR instance shared by
  several organizations, such as Epic Community Connect, cannot be split by base and is not
  supported). Whether each EHR binds its `launch` to the user who started it is the EHR's. Most
  EHRs send no `email_verified`, so the chain will mostly name launched clinicians
  `<issuer>|<subject>`. A browser holds one launch at a time: two charts launched one after
  the other in one browser end the first launch and leave its window saying it was replaced
  (it shows no patient, and the server refuses its reads), and the clinician launches it again
  from the EHR. Unregistering an EHR takes effect at the next restart or redeploy, not at once.
  In open mode with no EHR registered, a launch is as before: anyone the EHR lets launch decides
  in open mode's one organization. The launch is off unless configured (off in production, read
  in its signed-in `/api/health` on 2026-10-03).
- **People's sign-in rows are not sealed.** A `user` row keeps the person's name, verified
  email, issuer and subject and the claims their roles come from; an `oidc-pending` row keeps
  the sign-in's PKCE verifier for ten minutes. Neither holds a token. Sealing them would sign
  everyone out once; it is deferred to the PHI keyring work (ADR-0006).
- **The EHR's token stays valid at the EHR after a launch ends here** (logout, idle, a sealed
  row that does not open) until it expires: nothing is revoked at the EHR. The copy Mendari
  held is sealed, and an EHR that answers `401` ends the launch here too.
- **The feedback export's log line lists exported records only.** A rating left out of the
  export because its input was not kept, but whose note was opened, is chained (`input.read`)
  without a `phi.inputs.read` log line. The chain is the record that lasts.
- **Community packs are not clinically reviewed, and their risk level is self-declared.** A
  pack that under-declares its level is caught by the reviewer or not at all; the level cap
  (at most 1) and recommend-only serving bound the harm. Real patient data or licensed content
  merged by mistake cannot be fully taken back from a public history (forks and clones keep
  it): the PHI warnings, the provenance review and the DCO sign-off lower that risk, they do
  not remove it.
- **A registry nobody signs in to is run by command.** Since LP-19g there is no shared
  administrator token: on a registry of its own, claims, publisher types, reviews, the
  registry's recalls and deletions are the operator's commands on its database, chained with
  the command line's user and the reason given, which are only as true as the machine that ran
  them (R3). Under the engine a reviewer acts as a person, by id. Events from before LP-19g that
  name `admin` stay as they were written.
- **What a signed site report still does not show (LP-22).** A ticket binds a dataset before
  its run; it cannot show how the site chose its cases before it asked for one, so a site's
  evidence is shown apart from every rank, with the unreported tickets beside it. The
  registry's chain is still unkeyed (T7). A site's name is as good as the reviewer's check of
  who it is, done outside Mendari. A correction may use other data than the report it
  supersedes; both stay listed.
- **A registry that cannot be read holds its packs, after a while.** A server holds every pack
  pulled from a registry it has not read for a day (`MENDARI_REGISTRY_RECALL_STALE_S`), so an
  outage of the registry stops their automation (the safe direction). A server reads a
  registry's recalls only when a decision for one of its packs finds the last read older than
  the check interval (300 s), and that decision, like any made while the read runs, uses the
  list read before. A server that decides steadily has a recall within about the interval, or
  later while reads fail; after a quiet spell the first decision after a recall can still
  automate, and health's `checked_s_ago` shows the last read, not the registry's list. A hold
  (`POST /api/holds`) stops a pack within seconds, with no read. A serverless instance starts
  unread, so its pulled packs wait for its first read. `mendari decide` and `Decision.from_hub`
  know only the recall the last pull recorded. `GET /v1/yanks` is not paged: past a reader's
  5 MB cap every read fails, and a day later every pack from that registry is held.
- **The registry's chain is unkeyed.** Whoever can write the whole registry database can
  rewrite the chain with it; only a head kept elsewhere shows that (T7). The registry signs one
  on request (`mendari registry checkpoint`) and checks a kept one (`mendari registry verify
  --checkpoint`), but keeping it, daily and where the registry cannot write, is the operator's
  routine: nothing publishes or schedules it, a checkpoint says nothing about events appended
  after it, and whoever holds the signing key can sign any head. A review's note stays in the chain for
  good (a reviewer's or the operator's words about a pack, never case text).
- **The registry's signing key has no rotation path.** A client pins it at first contact
  (`@registry`). A recall it cannot verify is still honoured: safe for patients, but a forged
  recall can stop a pack's automation until someone looks (S19).
- **The regression check measures the publisher's own test set.** The publisher chooses the
  set, so the check can be gamed; it shows a regression and never refuses a version, and a
  first version has nothing to compare with. A pack whose default providers call a model is
  not measured (`needs_remote`). It runs in a child process of the registry's own user
  (`python -I`, a fixed environment of five variables, limits on CPU, file size and, where the
  system bounds it, memory: macOS does not), with no network or filesystem sandbox: accepted,
  since a pack's content is data and only local providers run (D11).
- **Smaller registry residuals.** An approval of a pulled pack's digest lasts until revoked; the
  publisher type the registry shows is the namespace's as it stands now, not when the version
  was published; and the Hub's own checks (its Playwright tests and the ZAP baseline in CI's
  `hub-site`, and the dashboard's approval screen in `browser`) are not required checks on
  `main`, so a pull request can merge with them failing.
- **Namespaces once taken stay taken (LP-19).** A refused claim keeps its name, and releasing a
  name or moving a namespace to another organization is not built; a lookalike that is not a
  reserved name is the reviewer's to refuse (S23). A publisher token is the organization's and
  keeps working when the person who made it leaves it: the revoking-access runbook says to
  revoke it (S22).
- **Clinical content** (pack criteria, rules, thresholds) is outside a security review. It
  needs clinician review and local validation, and every pack's card says so.
- **A CSP does not stop navigation.** A compromised script in a page could still navigate
  away carrying what it read. The vendored Swagger UI is protected by its pin, the integrity
  check and a review of each update (`scripts/vendor_docs_ui.py` lists the hosts a new bundle
  names), not by the CSP alone.
- **Synthetic data only** until the owner's go-ahead for real patients, after this review.
- **Limits are per instance clock and per region at the edge.** The app's buckets use each
  instance's clock (a skew of a second or two shifts a refill by as much), and Vercel's
  firewall counts per region. Neither matters at these limits.
- **The old cookie names, for one release.** On hosts that now use `__Host-` names, the plain
  `mendari_session` and `mendari_smart` still reach sessions made before Phase 4b (at most
  8 hours old at the deploy), so a planted plain-named cookie could name only such a session.
  The next release stops reading them (`tasks/todo.md`).
- **One database, one public URL.** Tokens and `jti` claims are rows in the deployment's
  database. Two deployments that share a database and a `MENDARI_PUBLIC_URL` (a preview
  pointed at production's database, say) accept each other's tokens and assertions. Give
  preview its own database, or keep Backend Services off there.
- **The key holder can decrypt hidden evaluation sets offline.** Whoever holds
  `MENDARI_EVALSET_KEY` and a copy of the database, or a sealed export (`mendari evalset
  export`), can open every case, label, aggregate and freeze record outside the server. "Only a
  grading run reads a frozen or active set" is a rule the software keeps (the routes and the
  grading read, I13; the lifecycle, T6), not the cryptography. The keys are the owner's, set as
  Secret for Production only, so a Preview's copy of the database holds the sets as ciphertext
  it cannot open (ADR-0011).
- **A draft's header has no commitment, an open assignment's end is not chained, and sets from
  before LP-11p are read as before.** A
  commitment the chain holds catches what it covers, changed by SQL or re-sealed offline: a
  case's input and own attributes (`case_ref`), a label (`label_ref`), each drawn case's weight
  (`weight_refs` on `evalset.sampled`, every drawn case at every draw, each with a new salt), a
  set's stored aggregates (`aggregates_ref` on the `evalset.measured` or `evalset.frozen` that
  stored them), and a frozen set's content (`evalset.frozen`, T6). A case's status stays clear
  text with no commitment of its own, and is checked against what is covered: its labels and the
  set's latest draw. Its labels are the ones the chain recorded, each in the round and by the
  labeller its `evalset.labelled` chained, never as an assignment row says now: a label row
  deleted, or one the chain never recorded, fails its case, and an adjudicator's label settles
  only a case whose two first-pass labels differ. So a status edited by SQL (a disputed case made
  `agreed`), a label deleted or an assignment moved to another round, a weight re-sealed or a
  case's attributes put back from before a draw, and aggregates re-sealed, put back or removed
  fail `mendari evalset rotate --check` and break `mendari audit verify --evalsets` (which also
  checks each assignment row against its `evalset.assigned`); `freeze`, `measure`, `assign` and
  `adjudicate` refuse a set whose labels, statuses or weights do not hold, naming no case (so no
  one is given a case on a status edited by SQL), and `show` and the curators' read refuse
  aggregates that do not, naming the set. What is not covered: until a set is frozen, its
  header, so a header re-sealed with the key passes and freezing commits to it as it is; an
  open assignment, which `assign` reads as its row says (one deleted by SQL breaks `verify`, but
  one ended by SQL looks like a withdrawal, which the chain does not record, and either gives
  the case to another labeller at the next `assign`); and the rows of a draw or a store from
  before LP-11p, which have nothing to check against. Those are read as before and counted
  (`predating`, a count, never an id): their statuses are still checked against their labels,
  but whether an unlabelled case was drawn, and its weight, are taken as they are until a draft
  is drawn again (a weight re-sealed or put back on such a draft passes every check and is
  frozen as it is), and its aggregates until it is measured again (on a set frozen before
  LP-11p, `show` reads them unchecked, so take its gate's positives from `freeze`'s output).
  Whoever can write the database can edit a status or put a value back, and re-sealing needs the
  evaluation-set key as well; each is caught when next read or verified, not prevented (T6).
- **An administrator can link one hidden case's events, and the chain keeps who labelled it.**
  Every event about a case names it by the same keyed hash (`hmac-sha256:<index key id>:…`), so
  an organization's administrators, in the administrative list and its FHIR export, can follow
  one case through being added, drawn (each draw names every case drawn so far, with a
  commitment to its weight, LP-11p, so the first draw naming a case shows when it was drawn),
  assigned, read, labelled and adjudicated, and see who read and labelled it, by user id; never
  what it holds, its stratum or weight, or how anyone labelled it (I13). The chain keeps
  those user ids for as long as it is kept: a labeller who leaves stays named there.
- **Adjudication shows where labellers disagreed.** A case given a third labeller
  (`evalset.assigned` in round `adjudication`) is one its first two labelled differently, so the
  chain shows which cases, and which pairs of labellers, disagreed, though not on which question
  or with which labels. The curators' read of a set counts its cases `disputed`, `resolved` and
  `unresolved`, and gives each pair's kappa (I13).
- **Paraphrases of public cases pass.** `mendari evalset add` takes hand-written cases only
  (`source` is `hand_written`, `template` is null) and refuses an input equal to a public case's,
  exactly or under `norm/v1`: the bundled reference data and example datasets, and each
  synthetic generator's output at its default seed. A reworded public case passes that check;
  only the rule, the author's care and review stand against it. The hidden-case index matches
  the same two forms, so the pack store's upload check (LP-20) will miss a reworded hidden case
  too.
- **A signed hidden-set result is the owner's attestation, and no one else can recompute it.**
  Anyone can recompute a public set's result from what the repository holds: its ledger, its
  dataset, its run record, its price table and the method (T8). A hidden set's answer
  (`mendari.hidden_scoreboard/1`, LP-17k) has no ledger: its cases never leave the deployment's
  database, and the grading read keeps nothing of them (ADR-0011). The results store checks the
  answer against its closed schema and against its own figures (each interval with its k and n,
  the evidence with its distinct positives, the grades, the banner and the ranking), and its
  signature covers the run's number. Its k and n, and so every grade it gives, are still the
  owner's word for what the deployment answered. The answer is bound to its run only by what
  the run's chained `evalset.graded` also holds (the set, its commitment, the pack's digest, n and
  the run's number), which an administrator of the deployment can compare with it; the chain
  holds none of its figures (LP-17 conflict 35: no new event kind). Grading the set again, one
  more of its runs, is the only second look.
- **Raw intervals on sets built from templates look narrower than they are.** Every figure on a
  public set is raw k of n with its exact 95% interval, and Clopper-Pearson takes the n cases as
  independent. A set generated from templates repeats its inputs: AI Guard's `test` set has 600
  cases but 81 distinct inputs under `norm/v1`, and 164 `verdict=block` positives but 30
  distinct. Its intervals are as narrow as 600 independent cases would give, so they overstate
  how sure each figure is. Against it: each scope names the set's distinct inputs beside n, the
  evidence rule and the grade's bound count distinct positives (a group detected only when every
  positive case in it is), the insufficient-evidence banner shows where they fall short, and
  nothing is ranked or graded on a public set (ADR-0013). The raw interval itself is not
  widened: that would change every published figure (`mendari.eval/2`, `Proportion.to_dict`).
- **The key holder could sign an altered result.** A signature says that Mendari's owner vouches
  for a result as it is (S20, E14); it does not make its figures right. A public result is
  recomputed from its stored inputs, and its local ledgers re-run, whoever signed it, so one its
  inputs do not give fails the store's check (T8); a remote configuration's ledgers are
  recomputed from, never re-run, so its decisions are the word of whoever ran it. A hidden set's
  answer cannot be recomputed at all: whoever holds `MENDARI_GRADING_SIGNING_KEY` could edit one
  so that it still fits its schema and agrees with its own figures, give it its new body hash,
  sign it and store it, and it would verify. What stands against it is around the key and the
  store, not the result: one key, held offline by the owner, never by a server or CI (E14); the
  review of each change to `scoreboard/`; the comparison with the run's chained `evalset.graded`
  above; and, for a key that leaked, taking it out of `scoreboard/keys.json`, after which nothing
  it signed verifies ([Verifying a scoreboard result](../grading/verifying.md)).
- **Trust in the EHR's key, and its rotation.** A token that verifies is the registered client's
  word (S21): Mendari checks that the client's key signed it, for the URL it was sent to, once,
  and nothing about who or what at the EHR made the call (a CDS Hooks token names the EHR, not a
  person, and `sub` is checked only when pinned). Whoever holds the EHR's private key can call
  as the client: the EHR's own systems and staff, its vendor's, or anyone who takes the key from
  them. What holds then is the client's confinement (E15): `discover` and `decide` on
  `/cds-services` only, in its one organization, reading only its registered FHIR bases, feedback
  only on the cards it asked for (R5), its rate limit and daily cap as `cds:<id>`, and each call
  chained as `cds <id>`; it reads no decision, no audit trail and no other route. Mendari learns
  that a key was retired only when it fetches the keys again. Keys from a `jwks_uri` are kept an
  hour on each instance (D13), so a key the EHR takes out of its JWK Set, a stolen one included,
  still verifies there for up to an hour, unless a token under a `kid` the kept keys do not hold
  makes that instance fetch sooner (at most once a minute) or it restarts; keys given by value
  verify until the registry is changed and the server redeployed. A key the EHR rotates in
  verifies from the first fetch after it: an instance that fetched in the last minute refuses its
  tokens (`cds_key`) until that minute has passed, so an EHR that switches keys at once can see up
  to a minute of `401`s on each instance, and a hook that gets one shows no card. To stop a client
  at once, take it out of `MENDARI_CDS_CLIENTS` and redeploy.
- **A compromised `jku` host.** A client registered by `jwks_uri` trusts whatever public keys
  that URL serves: the URL is pinned, its origin is on `MENDARI_FHIR_ALLOWED_SERVERS`, each
  token's `jku` must equal it exactly, and it is fetched through the allow-listed client (https
  but for a loopback or single-label host, no redirects, a size cap, public signing keys only).
  None of that tells a key the EHR published from one someone else put there. Whoever controls
  that host, its DNS or a certificate for its name can publish a key of their own; the next fetch
  (when the kept keys are an hour old, or at once for a token under a new `kid`, at most once a
  minute) keeps it, and their tokens are then the client's, with the confinement above and no
  more. A successful fetch is not logged, so nothing in Mendari shows the change. A client whose
  tokens carry no `jku` can be registered with its keys by value, which takes the host out of the
  trust at the cost of a redeploy for each rotation; a client registered so refuses any token
  that names a `jku`, and Epic's tokens name one (ADR-0014), so the Epic pilot trusts its host.
  The sandbox run records the `jku` Epic sends and whether it is always the same
  (`notes/epic-sandbox-checklist.md`).
- **The decision id disclosed to the EHR.** A card's `uuid` is its decision's id (I18), and with
  `MENDARI_PUBLIC_URL` set its link opens `/?pack=<pack>#audit/<id>`, so the EHR holds each id
  beside the patient and the order it sent, in whatever it keeps of the call (its logs, its own
  audit, its feedback, a vendor's copies), for as long as it keeps them. The id names no one (a
  random UUID 4 the engine made) and opens nothing by itself: a decision is read only with `read`
  in its organization, feedback on it is taken only from the client that asked for it (R5), and
  the trail holds no patient id (I17). The link is the EHR's: whoever holds the EHR's record of
  the call and Mendari's trail, or a copy of the chain, can tie each chained decision record (its
  pack, outcome, reasons and data-coverage counts, kept for good) to a patient, after Mendari's
  retention has removed the decision's input. Mendari's retention never reaches the EHR's copy.
  Treat a pilot's chain, exported or archived, as identifiable beside the EHR's records, under
  the site's agreements (B39).
- **A misconfigured site map.** `MENDARI_SITE_CODES` is checked at startup for its shape and its
  codes, not for its meaning (T9), and three mistakes pass. A translation into the wrong declared
  code reads a record as saying what it does not: the decision is capped at `HUMAN_REVIEW`, a
  rule's `BLOCK` included, so it reaches a person, whose recommendation is still built on the
  wrong code; its reason (`site code translated (<code set>): a person decides`) says that a
  translation was used, not that it was right. A site code the map leaves out reads as it would
  with no map, as no value: nothing was translated, so nothing is capped, and the pack decides
  (and may automate) as on a record without that code; only the decision's data-coverage record
  shows it, counting the coding under `other`. A map under another organization's key is applied
  to that organization's decisions (capped, as above) and missing from the intended one's (as a
  gap). Against these: each decision records its map's version and digest, `/api/health` shows
  the caller's, the cap holds until the site validates on its own chart-reviewed data (G5-6
  `site-validation`, owner decision 2), and of the reference packs only the Referral Router
  declares code sets (since LP-23k: its referral code, which a map's translation turns into the
  referrals it decides, and its checklist's document codes), so a map reaches that pack and any
  pack of the deployment's own that declares one.
- **A wrong declaration of what an EHR does not offer.** `MENDARI_EHR_DECLARATIONS` is checked
  at startup for its shape, its bases and the packs it applies to, not for its truth (T10). A
  declaration that MedicationStatement is not offered says the medications a pack should see are
  all MedicationRequests the EHR returns; if some are not (patient-reported home medications kept
  elsewhere, or as requests the list leaves out), a missing drug reads as not taken, for a person
  to check: the decision is capped at `HUMAN_REVIEW`, its reason names the limitation and who
  attested it, and its record the declaration's digest. Before setting it for Epic the site
  checks what `docs/guides/connecting-an-ehr.md` lists (where Epic keeps reported medications and
  with which `intent`, whether its search returns stopped and inpatient orders, whether a drug's
  name carries its generic name).
- **Frequent abstention on RTF-heavy records.** A pack on spec 0.3 reads a note as text only when
  it is text/plain or text/html (owner decision 9). An RTF, PDF or CDA note is `unsupported_type`,
  and a note none of whose renditions reads makes its decision ABSTAIN (`could not read notes:
  unsupported_type`). A pack before spec 0.3 abstains on a note that is only a link
  (`not_fetched`), and decodes a note's inline data whatever its type, so an inline RTF note is
  read with its markup; the trial and prior-authorization packs moved to spec 0.3 in LP-23k. On
  the vendor-shaped profile, whose notes are links, the trial and prior-auth patients with a
  text/plain or text/html note are decided on it since LP-23k, and the one with an RTF note
  abstains (`test_html_is_read_as_text_and_rtf_abstains`,
  `tests/test_ehr_profile.py::test_the_shipped_packs_read_the_profiles_linked_notes_through_the_allow_listed_client`). If Epic sends many
  notes as RTF, as the plan expects and only the sandbox run will show, those packs may abstain on
  most patients with a note. RTF is not the only cause on a real record. A hook reads every
  clinical note of the patient (`DocumentReference?patient=…&category=clinical-note`) and, for
  the trial pack, every MedicationRequest, and past a decision's budget (50 note Binaries, and
  apart from them 50 followed references: `linked.MAX_NOTE_READS`, `MAX_FOLLOW_READS`) each
  further link is `cap` and the decision abstains; and notes longer in all than the pack's input
  allows (20,000 characters for both packs) are left out of the input, never cut, and abstain
  (`too_large`, `fhir.overlong`, LP-23k; the notes past that point are not read), rather than let
  the schema refuse the whole input (a BLOCK, which shows no card). On a long history either may
  be the commoner cause. The first SMART launch on Epic's sandbox (2026-11-08) showed both kinds:
  the trial pack's test patient abstained with `notes: cap` and `notes: unsupported_type`, the
  second most likely the RTF twin of each capped HTML note (assumed: each Epic note an HTML and an
  RTF Binary, which the run's counts fit but cannot confirm, since they give no content types; a
  note's renditions now count once, by its text rendition's reason, `fhir.unread_notes`); its
  drugs were `cap` too, behind one budget of 20 that the notes had used. A note counted
  `unsupported_type` now has its format counted (`unread_formats`: `rtf`, `pdf`, `xml`, `image`,
  `none`, `other`), so a run with unread notes says how many of Epic's notes are RTF only (the
  2026-11-10 run read all 3 of its notes, too few to say). Each abstention goes to a person,
  which only lowers automation, and shows an
  `info` card whatever the pack's `show` says (owner decision 6), so the risk is workload and
  cards clinicians learn to pass over, not a wrong `AUTO`. Each decision's data-coverage record
  counts its unreadable notes by reason, so the sandbox run shows how often it happens; LP-23
  computes no rate from them. Reading RTF is not built: it waits on what the sandbox shows (owner
  decision 9).
