# v0.7 Later standards: plan

_Written 2026-09-30, during the overnight run. The user approved v0.4 to v1.0 in advance. Status
is tracked in `tasks/todo.md` and `docs/overnight-log.md`._

## Objective

Three more standards a health organization already uses:
- **CQL**, the language of eCQMs and clinical decision support, becomes a pack provider type;
- **OMOP**, the research data model, feeds packs for population-level evaluation;
- **Da Vinci CRD, DTR and PAS**, the payer standards for prior authorization, wrap the Prior
  Authorization Preflight pack.

**Exit:**
- the trial prescreener's structured criteria are computed by a CQL library and agree with the
  `criteria` provider on every case (CI);
- a synthetic OMOP database evaluates like the dataset it came from (CI);
- the PA pack answers CDS Hooks as CRD, serves DTR questionnaires for its gaps, and builds a PAS
  request, each validated against its Da Vinci IG by the HL7 validator (CI).

## Constraints

- **Nothing changes until it is configured.** A CQL variant is not a pack's default. OMOP is a
  command. The Da Vinci responses are additive: an EHR that ignores the CRD extension sees the
  same cards as before.
- **Pack artifacts are derived.** A new variant in a pack changes its digest. The reference-pack
  script reruns, and data, models, benchmark and card are committed together.
- **No real payer, no real data.** The payer is a sandbox mock, and every record is synthetic.

## Approach (one PR each)

### 1. A CQL provider
- **Provider type `cql`:**
  - `library`: a `.cql` file in the pack;
  - `expressions`: each answered question maps to a CQL expression, where true → `yes`,
    false → `no`, null → `unknown`, or to a label directly for string results;
  - `parameters`: the screening date, taken from an input field.
- **Evaluation** by a CQL engine behind the outbound FHIR guard: `Library/$evaluate` on a FHIR
  server with Clinical Reasoning (HAPI FHIR with `hapi.fhir.cr.enabled`), `useServerData=false`,
  and the patient's data sent as a Bundle.
  - The Library is uploaded once per content digest.
  - The server comes from `OPENHEALTH_CQL_URL` and must be on the FHIR allow-list.
  - Failures are `ProviderError`s with stable codes, and the policy's provider-failure cap turns
    AUTO into review.
- **Record → FHIR:** packs whose input is a record (conditions, observations, medications with
  codes) get a generic converter to R4 resources (Patient, Condition, Observation,
  MedicationStatement), so a CQL library reads them like EHR data.
- **Trial pack:** `logic/criteria.cql` computes the seven structured criteria. `criteria`
  stays the default. The new `cql` variant is compared on the leaderboard.
- **CI job `cql`:** HAPI with Clinical Reasoning in the compose sandbox. The CQL variant must
  equal the `criteria` variant on every test and dataset case.

### 2. OMOP CDM inputs
- **`openhealth omop dataset --db URL --pack ID`** reads an OMOP CDM 5.4 database (SQLite or
  Postgres):

  | OMOP table | Pack input |
  |---|---|
  | `person` | age at the screening date, sex |
  | `condition_occurrence` | conditions (ICD-10 from the source value, SNOMED from `concept`) |
  | `measurement` | observations (LOINC from `concept`, with value and unit) |
  | `drug_exposure` | medications (name, RxNorm, start and end) |
  | `note` | notes |

  It writes a local dataset, unlabelled or labelled from a site's own table.
- **Population evaluation:** `openhealth omop run` decides every person and reports the
  outcome mix and each criterion's unknown rate (metrics only, like shared reports).
- **Synthetic OMOP:** `openhealth sandbox omop` writes a small OMOP database from the trial
  pack's local-site dataset, with a minimal `concept` table for the codes used.
- **CI:** the OMOP database evaluates exactly like the dataset it was written from.

### 3. Da Vinci CRD
- The PA pack's `order-sign` service adds CRD's `coverage-information` extension to the order,
  in a system action:
  - `covered`;
  - `pa-needed`: `auth-needed`, `no-auth` or `satisfied`;
  - `doc-needed`: `clinical` when there are gaps;
  - `info-needed`, the coverage reference, the date and an assertion id.
- It adds a card linking to DTR when documentation is missing. Existing cards are unchanged.
- **Validated** against `hl7.fhir.us.davinci-crd` by the HL7 validator (CI).

### 4. Da Vinci DTR
- `POST /fhir/Questionnaire/$questionnaire-package` for an order: a Bundle with a DTR
  Questionnaire of the payer's required elements for the service, pre-answered from the record
  where the pack found them.
- **Validated** against `hl7.fhir.us.davinci-dtr` (CI).

### 5. Da Vinci PAS
- A PAS request Bundle (Claim, `use=preauthorization`, with Patient, Coverage, the payer's
  Organization, the requester and the ServiceRequest) for a complete request:
  `/api/packs/{id}/pas` and `openhealth pas build`.
- **Submission** to a payer's `Claim/$submit` (a sandbox mock payer answering a ClaimResponse)
  through the outbound guard.
- **Validated** against `hl7.fhir.us.davinci-pas` (CI).

## Verification
- [ ] The CQL variant agrees with `criteria` on every case, and a CQL server failure caps
      automation.
- [ ] OMOP round trip: the same decisions as the source dataset. The population report carries
      no case data.
- [ ] CRD, DTR and PAS resources pass the HL7 validator with their IGs, with no errors.
- [ ] Existing CDS Hooks responses are unchanged apart from the added extension.

## Risks
- **HAPI's Clinical Reasoning module:** its operations and configuration change between
  versions. Mitigation: pin the image, and exercise the exact call in CI.
- **Da Vinci profiles are strict** (X12 codes, identifiers). Mitigation: validate in CI from the
  first PR, and fill only what the IG requires.
